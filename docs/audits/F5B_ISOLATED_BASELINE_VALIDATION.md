## 9. Differences / defect

Exactly one, and it is a **BASELINE DEFECT** (capture-methodology gap):

- The F4 relation capture enumerated only `relkind in ('r','v','m')` (tables,
  views, matviews) and therefore **excluded SEQUENCES** (`relkind 'S'`). The
  snapshot recorded `categories.id`'s default expression
  `nextval('categories_id_seq'::regclass)` but never captured the owning
  `CREATE SEQUENCE`.
- `categories.id` is a serial-style `integer` primary key. It is the **only**
  sequence-backed column across all 39 tables (the other 38 use `uuid` PKs with
  `gen_random_uuid()`), so exactly one sequence (`categories_id_seq`) is missing
  and only `categories` is affected.

Classification: **BASELINE DEFECT.** Not a managed-infra difference, not a
bootstrap ACL difference, not UNKNOWN.

### Proposed correction (FOR REVIEW - not applied)

- **Preferred:** regenerate the canonical baseline from a service-role
  `pg_dump --schema-only` of the live project. `pg_dump` emits `CREATE SEQUENCE`
  (and serial/identity ownership) correctly, and also emits exact GRANT/REVOKE
  ACLs - which would resolve both this defect and the outstanding F5A
  grant-bootstrap uncertainty (section 7) in a single, authoritative artifact.
  This reinforces the F5A recommendation to author the final baseline from a
  service-role dump rather than from catalog reconstruction.
- **Minimal alternative (if staying catalog-derived):** add
  `create sequence if not exists public.categories_id_seq;` before the
  `categories` table and `alter sequence public.categories_id_seq owned by
  public.categories.id;` after it (or redefine `categories.id` as
  `integer generated by default as identity`), AND extend the F4/F5 capture
  methodology to include sequences (relkind 'S') and any other missed relation
  kinds, then re-validate.

Per instruction, the baseline was **not** patched or retried; this is for review.
